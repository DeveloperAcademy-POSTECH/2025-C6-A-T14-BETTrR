# 녹음 세션 상태·기기 경계·저장 정책

- 날짜: 2026-11-09
- 상태: 채택 — 설계 원칙이며 구현 완료는 관련 이슈에서 추적한다.
- 관련 이슈: [#319](https://github.com/DeveloperAcademy-POSTECH/2025-C6-A-T14-BETTrR/issues/319), [#292](https://github.com/DeveloperAcademy-POSTECH/2025-C6-A-T14-BETTrR/issues/292)
- 관련 결정: [0002](0002-feature-state-contract.md), [0004](0004-script-confirm-workflow.md)

## 배경

`RecordingViewModel`이 권한 요청, 음성 인식, 오디오 엔진, 타이머, 평가·저장을 함께
소유했다. 생성 시 권한 요청이 실행되었고, 인식 콜백·종료·취소가 서로 다른 시점에
같은 상태를 바꿨다. 종료 중 토글이 새 녹음을 시작할 수 있었고, 저장은 View의
`Task`에 묶여 화면 이탈 뒤에도 이동을 시도했다. 기기가 필요해 이런 경쟁을
자동 테스트로 확인할 수 없었다.

## 결정

MVVM을 유지하고 단계 전이만 순수한 상태 머신(`RecordingPhase`)으로 분리한다.
`RecordingViewModel`이 단계, 세션 ID, 타이머와 저장 Task의 수명을 소유한다.
View는 입력을 전달하고 상태·완료 결과를 표시한다.

- 단계: `대기 → 권한 요청 → 녹음 → 인식 마무리 → 결과 준비 → 평가/저장 → 완료`,
  실패는 `failed(원인)`. 허용되지 않은 이벤트(중복 시작·종료, 마무리 중 토글, 저장
  중 취소·재저장)는 전이 표가 거부하여 어떤 효과도 일으키지 않는다.
- 기기 경계는 작은 계약 세 개다: `RecordingPermissionProviding`(조회는 부작용
  없음, 요청은 명시 호출), `RecordingCapturing`(오디오 세션·엔진·인식의 시작,
  입력 종료, 해제), `RecordingClock`(타이머의 시간 원천). 실제 구현은
  `SystemRecordingPermissions`, `SpeechRecordingCapture`가 담당하며 기기 리소스의
  수명·해제 책임은 Capture 구현에 있다. ViewModel은 종료·취소·이탈 때 `release`를
  호출할 책임을 진다.
- 세션 ID는 녹음 시작마다 새로 만든다. 인식·권한 콜백과 저장 결과는 세션과 단계가
  일치할 때만 반영한다. 취소·재시작·이탈 뒤 도착한 늦은 콜백은 무시한다. Capture
  구현도 세대 번호로 이전 인식의 콜백을 버려 이중으로 방어한다.
- 권한은 생성이 아니라 첫 녹음 시작 이벤트에서 요청한다. 이미 허용되었으면 같은
  호출 안에서 바로 녹음하고, 거부 상태에서는 요청 없이 설정 안내를 표시한다.
- 시간은 `RecordingClock`의 단조 시계로 측정한다. 녹음 시간은 사용자가 종료한 시점
  (또는 인식기가 스스로 끝난 시점)에 고정하며, 인식 마무리 지연은 연습 시간에
  포함하지 않는다.
- 인식이 오류로 끝나도 그때까지 인식한 텍스트를 유지해 결과 준비로 진행한다.
  텍스트가 비어 있으면 평가 단계에서 `emptyTranscript`로 실패하고 저장하지 않는다.
- 평가와 저장은 View와 분리된 Task에서 실행하고 `self`를 결과가 올 때까지 유지한다.
  저장이 시작되면 취소·재저장을 거부한다. 화면 이탈 시 녹음·타이머는 정리하지만
  시작된 저장은 취소하지 않고 결과만 반영하며 화면 이동은 억제한다.
  UI 취소가 커밋 롤백을 보장한다고 표현하지 않는다([0004](0004-script-confirm-workflow.md)와 동일).
- 저장 결과 정책: 오류로 확인된 실패는 결과를 유지해 같은 데이터로 재시도할 수 있다.
  ID 없는 성공이나 `CancellationError`처럼 커밋 여부를 알 수 없으면 재저장을
  막고 기록에서 확인하도록 안내하여 중복 저장을 방지한다.
- 저장 성공 시 `RecordingCompletion`을 한 번만 전달하며(`consumeCompletion`),
  화면 이동은 View가 처리한다.
- 오디오 세션·엔진 시작 실패는 조용히 무시하지 않고 오류 알림으로 표시한다.

## 대안과 보류 이유

- 앱 전체 MVI/TCA 도입: 이 이슈의 문제는 한 화면의 전이이며 범위를 넘는다.
  전이 표 + ViewModel로 같은 검증 가능성을 얻는다.
- Capture를 권한·엔진·인식으로 더 쪼개기: 세 요소가 같은 세션·세대에 묶여 있어
  분리해도 검증할 독립 계약이 늘지 않는다. 필요해지면 `RecordingCapturing` 안에서 나눈다.
- 기존 `ScriptConfirmClock` 재사용: 호출 제한용 달력 시각이 섞여 있어 기능 간
  결합이 생긴다. 필요한 최소 계약(`now`, `sleep`)만 가진 별도 Clock을 둔다.
- 진입 시 권한 선요청 유지: 생성·표시의 부작용이 남고 테스트에서 분리하기 어렵다.
- 녹음 기능 모듈 추출: 이번 테스트 경계가 안정된 뒤 판단한다.

## 결과와 비용

기기 없이 성공·권한 거부·인식 실패·빈 결과·저장 실패·중복/늦은 이벤트·이탈을
검증할 수 있다. 전이 표와 Fake 세 종류를 유지해야 한다. 사용자에게 보이는 변화는
권한 프롬프트 시점(화면 진입 → 첫 녹음 탭)과 시작 실패 알림 추가다.
인식기가 마지막 결과를 끝내 보내지 않으면 `인식 마무리`에 머무는 한계는 그대로이며
이 경우에도 화면 이탈로 리소스는 정리된다.

## 검증

`RecordingPhaseTests`, `RecordingViewModelTests`, `RecordingAnalysisTests`가 Fake
기기와 Clock으로 실제 대기 없이 정책을 검증한다. 실제 iPad의 권한·녹음·평가·피드백
흐름은 #319 PR의 acceptance 체크리스트와 결과로 남긴다.

## 재검토 조건

인식 마무리 제한 시간, 앱 백그라운드·오디오 인터럽트 중 녹음 유지, 녹음 파일 보관,
온디바이스/서버 인식 전환, iPhone 지원이 제품 요구가 되면 Capture 계약과 세션
정책을 다시 결정한다. 다른 화면이 같은 기기 경계를 쓰거나 모듈 추출이 필요해지면
공개 계약을 이 기록 기준으로 재검토한다.
