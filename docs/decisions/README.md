# 아키텍처 결정 기록

ADR은 구조와 동작 규칙을 선택한 이유, 비용, 재검토 조건을 기록한다.
여기의 `채택`은 설계 원칙에 대한 결정이며 구현 완료를 의미하지 않는다.
구현 범위와 진행 상태는 [#292](https://github.com/DeveloperAcademy-POSTECH/2025-C6-A-T14-BETTrR/issues/292)
및 연결된 하위 이슈에서 관리한다.

| 기록 | 주제 |
| --- | --- |
| [0001](0001-script-persistence-boundary.md) | Script 복합 저장 경계 |
| [0002](0002-feature-state-contract.md) | 기능 상태 관리와 모듈 간 계약 |
| [0003](0003-ai-module-boundary.md) | BettrAI의 공개 계약과 의존성 경계 |
| [0004](0004-script-confirm-workflow.md) | ScriptConfirm 요청·타임아웃·저장 정책 |

각 결정의 상태와 대체 관계는 해당 ADR에서 확인한다.

## 문서별 책임과 갱신 기준

한 정보의 기준 위치는 하나만 둔다. 다른 문서에서는 링크하며 같은 규칙이나
체크리스트를 다시 적지 않는다. 문서 갱신은 모든 변경의 완료 조건이 아니다.

| 기준 위치 | 내용 | 갱신할 때 |
| --- | --- | --- |
| GitHub 이슈 | 작업 범위·선행 조건·완료 기준·진행 상태 | 범위나 진행 상태가 바뀔 때 |
| 로드맵 | 단계 목적·순서·착수 조건 | 단계나 의존 관계가 바뀔 때 |
| ADR | 중요한 경계·정책의 선택 이유·대안·비용 | 새로운 중요한 결정을 하거나 기존 결정을 대체할 때 |
| 기존 모듈 README | 사용하는 사람이 알아야 할 공개 계약·설정·실행 방법 | 사용 방법이나 외부 계약이 바뀔 때 |
| 기능 명세가 있는 경우 | 여러 변경에 걸쳐 유지할 동작·예외 계약 | 그 계약이 바뀔 때 |
| PR | 이번 변경 요약·검증 결과·미검증 범위 | 해당 PR에서만 기록 |

기존 계약을 만족시키는 버그 수정, 내부 파일 이동·리팩터링, 테스트 보강,
스타일 수정은 코드·테스트·PR 기록으로 충분하다. 이슈 완료만을 이유로
README·로드맵·ADR을 함께 갱신하지 않는다. 사용자 동작·공개 API·설정·의존
경계가 바뀌면 이를 설명하는 기존 기준 문서만 같은 PR에서 갱신한다.

## 문서를 추가하는 조건

먼저 기존 이슈·ADR·README를 활용한다. 닫힌 이슈를 반복해서 찾아야 하거나,
여러 작업이 같은 복잡한 동작 계약을 공유할 때만 작은 기능 명세를 추가한다.
관련 테스트를 링크하고 코드로 명확한 구현 세부 사항은 적지 않는다. 기존
문서에 해당 계약이 있으면 명세로 옮기고 링크로 대체하여 두 곳에서 관리하지 않는다.

현재 구조를 파악하기 어려울 때만 아키텍처 개요를 추가한다. 이미 README나
모듈 문서로 충분하면 별도 개요를 만들지 않는다. 기능·모듈마다 명세·ADR·
다이어그램을 일괄 생성하지 않으며, Spec Kit·OpenSpec 도입은 별도 판단한다.

현재 ScriptConfirm의 핵심 정책은 ADR 0004를 기준으로 유지하고, 세부 수락
시나리오와 완료 기준은 #306에서 추적한다. 별도 명세를 선행 생성하지 않는다.
새 문서에는 적용 범위와 구현된 계약인지 제안인지 표시한다.

## 읽기와 유지

관련 이슈 → 직접 연결된 기준 문서 → 필요한 코드·테스트 순서로 확인한다.
관련 없는 문서 전체를 매번 읽거나 재작성하지 않는다. 테스트 실행 기록은 PR에
남기고, 진행 상태와 갱신 날짜를 여러 문서에 복제하지 않는다. 단순한 진행에는
이 목록도 수정하지 않는다. 기준 위치를 옮기거나 새 기록을 추가할 때만 링크를 정리한다.

## 작성과 변경

[템플릿](template.md)으로 주요 결정마다 하나의 ADR을 작성한다. 구현 전에
`제안`으로 기록하고, 검토하여 방향을 정하면 `채택`으로 바꾼다. 작은 구현
선택은 PR에 남기며 별도 ADR을 요구하지 않는다. ADR은 결정과 이유를 중심으로
짧게 작성하고, 작업 목록·전체 테스트 시나리오·실행 결과는 링크한다.

채택된 결정을 바꾸는 경우 새 ADR을 작성하고 이전 기록을 `대체됨`으로
표시하여 서로 연결한다. 이전 결정의 이유는 삭제하지 않는다. 오탈자나 설명
보완은 기존 기록에 반영할 수 있다. 기존 0001은 원래 기록을 유지한다.

상태나 일정 변경은 이슈에서 처리하며, 설계 결정 자체가 바뀔 때 ADR을 갱신한다.
