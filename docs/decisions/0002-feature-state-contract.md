## 배경

기존 기능에는 ViewModel이 있지만, 일부 View가 외부 호출·저장·화면 이동을
조율한다. 의존성 컨테이너에도 서비스 조립과 목록 상태가 함께 있다.
모듈화에서는 기능 내부의 구현 방식보다 상태 소유권과 공개 경계를 먼저 정해야 한다.

## 결정

기능의 기본 구조는 MVVM으로 유지한다. 녹음·AI 분석처럼 비동기 상태 전이가
복잡한 기능은 명시적 상태 머신이나 리듀서를 사용할 수 있다. 앱 전체의 MVI
전환이나 TCA 도입은 요구하지 않는다.

- 기능 상태는 ViewModel 또는 Store 한 곳이 소유한다. 다른 객체가 같은 상태를
  독립적으로 갱신하는 대신, 해당 소유자에서 결과를 반영하거나 값을 도출한다.
- View는 렌더링과 사용자 입력 전달을 맡고, 포커스·애니메이션 등 로컬 UI 상태를
  소유할 수 있다. 외부 호출과 저장의 업무 흐름은 View 밖에서 조율한다.
- 앱 시작점의 Composition Root가 실제 구현을 조립한다. 기능에는 필요한
  의존성만 전달하고, 화면 데이터는 조립 컨테이너와 분리한다.
- 모듈의 공개 인터페이스에는 진입 입력과 완료·취소 결과를 제공한다. 다른
  기능이 내부 ViewModel·Store·Action에 의존하지 않게 한다.
- 취소·중복 요청·늦은 응답·오류 전달은 기능별로 명시하고, 외부 서비스 없이
  검증할 수 있게 한다.

내부 상태 관리 방식이 달라도 위 계약을 따른다. 추가 Feature 모듈은 독립
테스트, 변경 영향, 코드 소유권, 빌드 비용 등 관찰된 필요를 근거로 선택한다.
모든 기능을 일괄 추출하거나 동일한 패턴으로 다시 작성하지 않는다.

## 대안과 보류 이유

- 전면 MVI·TCA: 현재 첫 모듈의 목표는 AI 의존성 격리다. 전체 상태 관리 방식의
  변경 비용을 정당화할 반복적인 문제가 확인되기 전까지 보류한다.
- 모듈마다 제한 없이 패턴 선택: 취소·오류·테스트 규칙이 달라지고 협업 비용이
  커질 수 있어, 내부 구현의 선택과 공통 계약을 함께 둔다.
- 모든 View에 ViewModel 추가: 단순한 로컬 UI 상태까지 옮길 필요는 없다.

## 결과와 비용

기존 MVVM을 활용하면서 복잡한 흐름만 강화할 수 있다. 대신 기능별 상태
전이와 공개 계약을 문서화하고 리뷰해야 한다. 모듈 추출만으로 상태 소유권이나
비동기 경쟁 문제가 해결되는 것은 아니므로 추출 전에 검증한다.

## 검증

기능 테스트에서 외부 구현을 Fake로 교체할 수 있고, 주요 성공·실패·취소 흐름을
View 없이 확인한다. PR에서는 상태 소유자, 의존성 주입 위치, 공개 API에 내부
상태 관리 타입이 노출되는지를 검토한다. 기존 iPad 정상 흐름은 회귀 검증하고,
경쟁 상황의 변경 동작은 해당 이슈의 완료 조건으로 명시한다.

## 재검토 조건

여러 기능에서 상태 합성·효과 취소·공유 세션 복원 문제가 반복되거나, 팀의
숙련도와 테스트 요구가 특정 라이브러리 도입을 뒷받침하면 공통 상태 관리
방식을 다시 검토한다. 모듈 추출의 이점과 공개 경계는 실제 변경·테스트 경험으로 판단한다.
