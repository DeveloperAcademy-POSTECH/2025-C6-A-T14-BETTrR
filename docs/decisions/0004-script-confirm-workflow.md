# ScriptConfirm 요청·타임아웃·저장 정책

- 날짜: 2026-10-05
- 상태: 채택 — 설계 원칙이며 구현 완료는 관련 이슈에서 추적한다.
- 관련 이슈: [#306](https://github.com/DeveloperAcademy-POSTECH/2025-C6-A-T14-BETTrR/issues/306), [#294](https://github.com/DeveloperAcademy-POSTECH/2025-C6-A-T14-BETTrR/issues/294), [#304](https://github.com/DeveloperAcademy-POSTECH/2025-C6-A-T14-BETTrR/issues/304)

## 배경

ScriptConfirm View가 AI 호출, 타임아웃, 저장과 화면 이동을 조율한다. 요청
취소 뒤의 응답이나 이전 타이머가 다음 요청에 영향을 줄 수 있고, 저장 중
취소와 저장 완료의 의미도 구분해야 한다. 정상 흐름을 유지하면서 경쟁 상황을
View 없이 검증할 수 있는 책임 경계가 필요하다.

## 결정

ViewModel 또는 Coordinator가 명시적 단계와 요청 ID를 소유한다. 단계는
`대기 → 분석 중 → 저장 중 → 완료`를 기본으로 실패·취소를 표현한다.
View는 입력을 전달하고 상태를 표시하며, 저장 완료 결과로 화면 이동을 수행한다.

- 요청 시작 시 입력과 제목을 고정한다. 저장과 완료 결과는 해당 요청의 최종 제목을 사용한다.
- 중복 실행·호출 제한 검사를 통과하여 요청을 수락한 뒤 요청 ID와 분석
  타이머를 시작한다. 거부된 입력은 새로운 요청이나 타이머를 만들지 않는다.
- 30초 제한은 AI 분석과 그 재시도 대기를 포함한다. 분석 결과를 받아 현재
  요청임을 확인한 뒤 분석 타이머를 종료하고 저장 단계로 전환한다.
  DB 저장에는 이 분석 타임아웃을 적용하지 않는다.
- 비동기 결과와 타이머 이벤트는 요청 ID 및 현재 단계가 일치할 때만 반영한다.
  이전 요청의 결과가 후속 요청 상태를 바꾸지 못하게 한다.
- 취소·화면 이탈·분석 타임아웃은 해당 요청의 UI 처리 수명을 끝낸다.
  이후 새로운 AI 재시도와 저장을 시작하지 않고, 늦은 응답은 무시한다.
- 이미 시작된 DB 트랜잭션은 커밋 또는 롤백될 수 있다. UI 취소가 저장
  롤백을 보장한다고 표현하지 않는다. 화면 이탈 뒤에는 화면 이동을 억제한다.
- 저장 결과가 불확실하면 저장 계층의 결과와 조정하고, 저장이 실패했음을
  확인하기 전에는 같은 데이터를 다시 저장하지 않는다. 이미 저장된 결과는
  재호출로 중복 생성하지 않는다.
- 저장 실패가 확인된 경우 파싱된 초안을 보관하여 AI를 다시 호출하지 않고
  저장을 재시도할 수 있다. 초안의 보관 기간은 해당 기능 수명 안으로 제한한다.
- 저장 성공 시 `savedID`와 제목을 포함한 완료 결과를 한 번 전달한다.
  화면 이동은 UI가 처리하고, 완료 결과 중복 소비를 방지한다.

저장의 원자성은 [0001](0001-script-persistence-boundary.md)을 따른다.
저장 단계의 실패·진행 상태는 분석 실패와 구분하여 사용자에게 전달한다.

## 대안과 보류 이유

- View에서 Task·타이머 조율 유지: 수명과 요청 간 경쟁을 View 없이 검증하기 어렵다.
- 분석·저장 전체에 동일한 30초 제한 적용: 커밋된 저장을 분석 타임아웃 실패로
  표시할 수 있어, 분석 제한과 저장 결과를 분리한다.
- 취소 시 저장 롤백 보장: UI 취소만으로 이미 진행된 DB 커밋을 되돌릴 수 없다.
- 저장 실패 시 전체 분석 재실행: 유효한 초안이 있으면 비용과 결과 변동을 피할 수 있다.
- MVI 필수 적용: 명시적 상태와 테스트 가능성을 만족하는 ViewModel도 허용한다.

## 결과와 비용

요청과 화면의 수명, AI 제한 시간과 저장 결과를 구분할 수 있다. 요청 ID,
단계 전이, 초안 보관 및 저장 결과 조정 로직을 관리해야 한다. 저장 중 취소
이후에도 데이터가 생성될 수 있다는 제품 동작을 화면·오류 처리에 반영해야 한다.

## 검증

Fake AI, 저장소, 제어 가능한 Clock으로 요청 경쟁·취소·저장 실패를 View 없이
검증한다. 세부 수락 시나리오와 완료 기준은 관련 이슈 #306에서 관리하고,
테스트 실행 결과와 기존 iPad 정상 흐름의 통합 검증은 PR에 남긴다.

## 재검토 조건

제품 요구가 전체 처리 시간 제한, 앱 재시작 뒤 요청 복원, 백그라운드 저장 또는
장기 초안 복원을 요구하면 요청 수명·저장 정책을 다시 결정한다. 모듈 추출은
이 흐름의 독립 테스트와 공개 계약이 안정된 뒤 검토한다.
